# 压测方案文档模板（plan.md）

> 写在方案包目录 `<案例库根>/load/task_<任务id>/plan.md`。这是「跑之前给人看」的东西：
> 读完它应当能回答「压谁、压多狠、看什么、怎么算通过」。

## 格式要求（硬要求：必须是 Markdown）

平台「压测方案」页用 markdown 渲染器直接渲染 plan.md，只有下面这些语法会成排版：

| 语法 | 渲染结果 |
|------|----------|
| `# 标题` / `## 1. 小节` / `### 子节` | 文档标题 + 章节（`## 1.` 的序号会被拆成金色标注，并自动生成左侧目录） |
| 紧跟标题的一段 `- 键：值` 列表（≥2 项） | 抬头栏（目标服务 / 执行载体 / 生成时间…逐行成对展示） |
| 管道表格（表头行 + `---` 分隔行，列用竖线分隔） | 表格（**必须**用管道表格；空格对齐的伪表格只会渲染成一堆文字） |
| `- 项` / `1. 项` | 无序 / 有序列表 |
| 反引号包住 `code` | 行内代码（路径、指标名、字段名都走它） |
| `> 引用` | 提示条（放「为什么这么设计」的依据段） |
| 三反引号围栏 | 代码块（复现命令、请求体示例） |

**不要**：整篇纯文本、用空格/制表符对齐的伪表格、用 `====` 或 `----` 手画表格线、
把多个字段塞进一行长句。表格里较长的一列（说明/依据）正常写，渲染器会自己排。

```markdown
# 压测方案：<被测对象 / 场景名>

- 目标服务：http://127.0.0.1:8080（来源：任务压测说明 / 代码配置）
- 执行载体：scenario.json（内置 HTTP 引擎） 或 run.py（自定义脚本）
- 生成时间：YYYY-MM-DD HH:MM

## 1. 目标与范围

<为什么压、压什么、不压什么。例如：验证下单链路在高并发下的吞吐与延迟上限，
不覆盖支付回调（沙箱不可用）。>

## 2. 被测接口

| 接口 | 方法 | 路径 | 说明 | 权重/占比 |
|------|------|------|------|-----------|
| 下单 | POST | /api/order | 主链路写接口 | 3 |
| 查询 | GET | /api/order/{id} | 读多写少 | 7 |

<请求体/鉴权/前置数据准备的说明；说明里没给的，写明「按代码 X 文件推断」。>

## 3. 加压模型

| 档位 | 并发 | 时长 | 说明 |
|------|------|------|------|
| 1 | 10 | 60s | 预热 |
| 2 | 50 | 120s | 稳态 |
| 3 | 100 | 60s | 上探 |

<超出平台容量边界（并发 ≤512）时的说明。>

## 4. 指标定义（与 charts.json 一致）

| 指标名 | 类型 | 含义 | 来源 |
|--------|------|------|------|
| rps | gauge | 每秒请求数 | 引擎/脚本统计 |
| lat.p95 | gauge | 95 分位延迟（ms） | 延迟分桶插值 |
| lat.p50/lat.p90/lat.p99 | gauge | 其它分位 | 同上 |
| err.rate | gauge | 错误率（0~1） | 错误数/请求数 |
| req.total / req.errors | counter | 累计请求数 / 错误数 | 累计计数 |
| order.status | counter | 各状态委托数（labels.status） | 业务侧统计 |

<自定义指标必须写清「怎么算出来的」，否则图上的数没法解释。>

## 5. 图表设计

<本方案要在面板上看的图（与 charts.json 对应），一句话一张图。>

## 6. 通过标准与风险

- 通过标准：<如 P95 < 200ms 且错误率 < 1%>
- 已知风险：<如目标服务未做压测环境隔离、依赖外部第三方接口>
- 回滚/停止条件：<如错误率连续 30s 超过 5% 时应人工停止>
```
